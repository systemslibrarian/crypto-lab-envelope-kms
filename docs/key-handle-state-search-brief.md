# Bounded key-handle state-search brief

This is the second E-K-01 extension. It adds a finite state explorer beside the
original manual key-handle trace without changing `HandleToken`, the normal KMS
API, or either API's defaults.

## 1. Claim and invariant

The explorer asks one reachability question:

> Can the modeled attacker place `protected-target` in its set of known raw key
> values within the displayed operations and bounds?

The invariant is therefore `protected-target not in attacker-known raw values`.
A witness is a shortest sequence of successful API calls that violates this
invariant. A completed search with no witness is reported only as bounded
evidence. A resource cutoff is reported as **search incomplete**, never as a
safe result.

The explorer tracks symbolic key-value identities separately from handles. Two
fresh handles can therefore be distinct objects whose underlying values are
equal while their per-handle permissions differ. “Alias-state” is roadmap
shorthand for this same-value condition; it is not a claim that PKCS #11
returned two handles to one object.

## 2. Attacker and state

Every state records:

- public handles and, for each, its symbolic value, capabilities, sensitivity,
  and extractability;
- known AES-KW blob terms `kw(wrapper-value,payload-value)`;
- raw values known to the attacker;
- the fresh-handle counter used to render a witness.

The attacker controls API call order, public handle arguments, and, under the
unsafe policy, one of three caller templates. It initially knows exactly what
the selected preset displays. It cannot guess an AES key, bypass RFC 3394
integrity, break AES-GCM authentication, read a sensitive object directly, or
use an operation omitted from the alphabet. Local AES-KW unwrap is available
only when the attacker knows the exact wrapping-key value.

Capabilities are mechanism-qualified:

- `KW_ENCRYPT_BYTES`
- `KW_WRAP_KEY`
- `KW_UNWRAP_KEY`
- `KW_DECRYPT_BYTES`
- `GCM_OPEN_DATA`

`KW_DECRYPT_BYTES` is not AES-GCM data opening.

## 3. Transition alphabet

1. `EncryptKnown` requires `KW_ENCRYPT_BYTES` and a raw value already in
   attacker knowledge. It emits an AES-KW blob.
2. `WrapKey` requires `KW_WRAP_KEY` and an extractable target object. It emits
   an AES-KW blob.
3. `UnwrapAs` requires `KW_UNWRAP_KEY` and a blob wrapped by that handle's key
   value. The unsafe policy accepts `data-only`, `kw-wrap-only`, or
   `kw-decrypt-only`; the fixed policy accepts only `data-only`. A successful
   call allocates a fresh sensitive, nonextractable handle.
4. `GrantKwDecrypt` exists only in the unsafe mutable-role preset and adds
   byte-returning AES-KW decryption to a handle that already has the wrapping
   role. It is not part of either import preset, so those witnesses test
   template and same-value behavior.
5. `DecryptBytes` requires `KW_DECRYPT_BYTES` and a matching blob, then adds
   the plaintext value to attacker knowledge.
6. After a successful call, local knowledge closure unwraps every known blob
   whose exact wrapping-key value the attacker already knows. This is an
   attacker deduction, not an API call.

Rejected calls do not allocate an object, emit a blob, alter state, or consume
successful-call depth. Omitting them cannot create a shorter reachability
witness.

## 4. Exact bounds and algorithm

The browser performs deterministic breadth-first search with:

- at most four successful API calls;
- two atomic values in the original mutable-role preset, or exactly three in
  either import preset;
- at most four live handles;
- at most four distinct AES-KW blobs;
- exactly three finite unwrap templates;
- a default operational cap of 50,000 retained non-witness states; the UI also
  offers a one-state setting solely to make incomplete-search handling
  observable.

Canonical state identity includes the multiset of object value/capability/
attribute descriptions, all blob terms, and all attacker-known values. Fresh
handle spelling is ignored, but object multiplicity is retained, so two
same-value handles are not collapsed into one. The predecessor path remains on
the breadth-first node and produces the displayed shortest witness.

Every generated successor is checked for an invariant violation before
non-witness retention. A terminal witness is reported immediately and may be
the one additional state beyond the retained-state count. If retaining a new
non-witness state would exceed the operational cap, the search stops as
incomplete. This ordering prevents a cap-triggering non-witness sibling from
hiding a witness generated by the same expanded state. “No witness within
bounds” is emitted only after every reachable distinct state through depth four
has been processed.

## 5. Executable presets

### Mutable wrapping role

This re-searches the original manual trace. The protected target is sensitive
and extractable. An internal transport handle can wrap and unwrap keys. Under
the unsafe policy the search wraps the target, grants the same transport handle
`KW_DECRYPT_BYTES`, then decrypts the blob. The fixed policy rejects the grant.

### Known-key import and template confusion

Initial knowledge contains raw `caller-known-key` bytes plus public target and
importer handles. The importer has `KW_ENCRYPT_BYTES` and `KW_UNWRAP_KEY`, but
its bytes remain unknown. The unsafe witness is:

1. AES-KW-encrypt the caller-known value under the importer;
2. unwrap it with a caller-selected `kw-wrap-only` template;
3. wrap the protected target with that new handle;
4. outside the API, unwrap the last blob with the already-known caller key.

Only the first three steps are API calls, so the witness depth is three. The
fixed policy rejects the wrapping template and may create only a data-only
handle.

### Same-value handles with conflicting roles

Initial knowledge contains an opaque blob `kw(transport-key,opaque-pivot)` but
neither raw value. The importer has `KW_UNWRAP_KEY`. The unsafe witness unwraps
the same blob twice: one fresh handle requests `kw-wrap-only`, and the other
requests `kw-decrypt-only`. It then wraps the target with the first handle and
returns its bytes through the second. The two handles are distinct but contain
equal pivot bytes. The fixed policy can create data-only handles but cannot
assign either conflicting AES-KW role.

These are bounded teaching adaptations of historical API-composition attacks,
not claims about a particular token or current vendor implementation.

## 6. Concrete cryptographic replay

The symbolic witness is the sole source of the displayed call trace. Only after
search succeeds does `replayKeyHandleWitness` execute that exact witness using
fresh, distinct AES-256 values and the existing RFC 3394 implementation.

- Every wrapped 32-byte value produces a real 40-byte AES-KW blob.
- Duplicate unwraps recover equal bytes into distinct runtime handles.
- Local attacker unwrap uses only a key already present in attacker knowledge.
- The recovered target must equal the original target bytes.
- Those recovered bytes must independently authenticate and open a fresh
  AES-256-GCM challenge.

Symbolic reachability and concrete cryptographic replay are reported separately.
RFC 3394 integrity-checks the 32 key bytes in this implementation's blob; this
adaptation does not claim that its caller-selected role template is bound into
or integrity-checked by that 40-byte blob.

## 7. UI and accessibility

The learner chooses a preset and fixed or unsafe policy, then explicitly starts
the search. Changing either input retires the prior result. The UI always shows
the invariant, initial knowledge, transition rules, bounds, state cap, and
limitations. A witness shows the search-derived API sequence plus replay bytes;
its terminal evidence separately shows attacker-known values and retained
same-value handle identities and roles. A fixed result shows the exact states
and accepted transition instances checked.

The result is announced through a live status region, focus returns to the
initiating button, all controls are keyboard operable, and the layout reflows at
380 CSS pixels. Exposure, bounded completion, incomplete search, and runtime
error have text labels in addition to color.

## 8. Tests and mutations

Unit tests require deterministic shortest witnesses at depths three, three, and
four; misses one step below those depths; complete fixed-policy searches; a
separate incomplete result under a tiny state cap; distinct same-value handles;
terminal-state evidence consistent with the replayed witness; valid fixture
ownership; real RFC 3394 replay; and independent WebCrypto GCM opening. Browser
claims use only rendered bytes to open the displayed challenge.
Accessibility tests exercise the initial, bounded-complete, import-exposure, and
same-value-exposure states at narrow and desktop widths.

Focused mutations must be caught if the fixed policy accepts a privileged
caller template, the same-value handle state collapses object multiplicity,
displayed escaped bytes are fabricated, a cutoff is mislabeled as complete, or
the visible bounded-model limitation is removed. Run mutations only from a
committed clean baseline; the runner must restore source and re-check that
baseline immediately.

## 9. Limits

This is not a PKCS #11 implementation, HSM assessment, vendor vulnerability
claim, exhaustive search, or security proof. The fixed roles and fixed template
block the modeled traces; they do not establish security for unmodeled
copy/derive calls, mechanisms, sessions, authentication, concurrency, runtime
compromise, side channels, or larger resource bounds. The fixed template is
deliberately narrower than the general templates a conforming PKCS #11
implementation may support.
